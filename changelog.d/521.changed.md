`held_keys` through ORWU NPHASKEY (#521)

- `Authentication.held_keys` asks `ORWU NPHASKEY` once per named key for the signed-on DUZ (`NPHASKEY^ORWU(VAL,NP,KEY)` = `''$D(^XUSEC(KEY,NP))`), with the batch bound to `OR CPRS GUI CHART`, instead of one VueCentric-only `CIAVCXUS HASKEYS` call. Over CIA the context rides on each frame, so N keys cost N frames. Over XWB/BMX the cost is N when `OR CPRS GUI CHART` is already bound, and N + 2 (a bind and a restore) otherwise: `ContextScope#with_context` does nothing when that option is already bound, and `Client#create_context` binds it by default. Over XWB/BMX the bind is a menu check (`$$CHK^XQCS`), so a user whose menu lacks `OR CPRS GUI CHART` gets nil (could not ask). On CIA each call is a normal client RPC, so the client numbers the frame and the session sequence advances with the batch. `MockClient` now carries the signed-on DUZ (`set_authenticated` / `clear_authenticated` / `duz`). `MockClient` answers `ORWU NPHASKEY` only for a seed under the full [DUZ, KEY] list, so a DUZ-only seed no longer reads every key as held (in `has_security_key?` too). The DUZ is read inside the scope, under the wire lock, and that value is NP for every call in the batch. A refused bind (scope entry or nested) re-binds the caller's previous context; if that is refused too, `current_context` is nil (`CRCONTXT^XWBSEC` kills the broker context on XWB/BMX, and `Client#create_context` clears it on failure; `MockClient#create_context` does the same on `unbindable_context!` or a context-surface refusal). CIA's bind is client-side and is unchanged.
- The return contract is unchanged: the subset held, in the order asked; `[]` when none are held; `nil` when the question could not be asked. No signed-on DUZ (no `#duz`, or nil, blank, or non-positive) returns `nil` without sending `ORWU NPHASKEY`; on XWB/BMX the context bind and restore may still be sent. A not-authenticated client raises before anything is sent and also returns `nil`. Altered replies are nil. A refused call, an empty reply, or any answer other than exactly `"0"` or `"1"` (the one normalised data line, compared exactly) returns `nil` for the whole batch. Blank names are dropped; an all-blank list sends nothing and returns `[]`. A name containing `^` or a leading `@` raises `ArgumentError` before anything is sent.
