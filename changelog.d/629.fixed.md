Health-factor and Wellness saves of one visit share one exclusion, and a visit-lock wait no longer holds the wire (#629)

- `BehavioralHealth.save_health_factors`, `Wellness.save_screening` and `Wellness.save_measurements` take one in-process exclusion per client and record (`BehavioralHealth::SaveGuard`). Before, each kept its own set, so a health-factor save and a Wellness save of the same visit on one client ran together: M LOCK is incremental per broker job, so the broker granted the second the lock the first held. The second save is now refused with SaveError ("in progress") before any RPC.
- The visit lock is polled (`DDR LOCK/UNLOCK NODE` with a zero timeout, then a half-second pause with the wire free, about five seconds in all) instead of one server-side five-second wait. The health-factor save waited with the client's wire lock held, so every other caller on that client blocked behind it; now they run between polls.
- Proven live on bcer-9.0-20261119-f67498c-ydb-demo as PROV123: a second broker job holds the visit lock, and while the health-factor save waits, a Wellness save of that visit on the same client is refused and an RPC on that client answers; both saves land once the lock is released (`test/live/behavioral_health_save_health_factors_live_test.rb`).
