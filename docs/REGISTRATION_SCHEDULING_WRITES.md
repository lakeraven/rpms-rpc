# Registration and scheduling writes (rpms-rpc#418)

Evidence is from the pinned bcer YDB build: a tag-level reverse call graph over the routines in `/data/r` (external `TAG^RTN` refs, local tag refs, and fall-through, depth 6), intersected with every `#8994` `TAG^ROUTINE`. Indirection (`@X`, `XECUTE`) was not followed. `#8994` was read from `^XWB(8994)`.

Resolution 1 is a stock RPC that already reaches the M tag. Resolution 2 is DDR FILER or DDR LISTER, because no `#8994` entry reaches the tag and the FileMan write or read is the whole of what the tag does to those fields. Resolution 3 is not supported: the gem method sends no RPC, because a FileMan write would not be what the M routine does.

## What DDR FILER skips

`DDR FILER` is `FILEC^DDR3` (`DDR3.m:14-18`). Mode `ADD` is `UPDATE^DIE`. Any other mode, including the `EDIT` that deletes a holiday by setting `.01` to `"@"`, is `FILE^DIE`. Both run with no `"E"` flag (`DDR3.m:15,18`), so the value is filed internal. The RPC does not translate an external code, apply a default the M tag would have stuffed, prompt the way an interactive `DIC`/`DIE` does, or update a file the tag updates in its own code.

FileMan triggers and MUMPS cross-references on the fields that are filed still run, because the write is FileMan. That is why the SOGI xrefs and the MBI field triggers do not have to be called by name.

The client supplies the values those tags would have put in the FDA, and nothing else.

`FILEC^DDR3` emits `[Data]` first on a completed call (`DDR3.m:19-23`). `DdrFileman.filer` sets `success` true only when the reply contains `[Data]` and the `[BEGIN_diERRORS]` block is empty. A reply with no `[Data]` is `success: false`; `errors` names the missing marker and includes the reply's first line. nil is still no broker response. The `+n,^IEN` placeholder parse is unchanged. Writers built on `filer` (`Registration` SOGI, legal sex, MBI, and `set_sex`, and `SchedulingSetup` holidays) use that `success` flag and do not re-check the marker. A reply with no `[Data]` is `:filer_failed`, or `:partial` when `set_sex` has already filed an earlier EDIT. A no-reply (nil) is unchanged.

Each dated write lists the date rows with DDR LISTER (`file` the subfile, `iens` `",<dfn>,"`, `fields` `"@;.01I"`, `flags` `"IP"`) before it files. A packed row is IEN-first (`IEN^` internal `.01`). DDR GETS ENTRY DATA cannot tell a missing row from a failed read: GETS on a missing entry replies `error: true`. Gender identity and sexual orientation read each distinct value's code file first (field `1`, flags `I`). A genuine `[ERROR]` reply is the unknown-code answer (`$$GI^AUTSOGI` / `$$SO^AUTSOGI(val,"I")` returns `""`), so it is `{ success: false, error: :invalid }` and the date rows are not listed. A reply with neither `[Data]` nor `[ERROR]` and no field rows (`malformed: true`) is checked before that and is `:lookup_failed`; the message names the file and field, the same way a malformed `#2` `.02` or `#9000001` `.23` read does. A nil reply on that code read is `:lookup_failed`. DDR GETS returns a row even for an empty field, so a `[Data]` reply with no row for field `1` is `:lookup_failed` as well, and nothing is filed (no DDR LISTER, no DDR FILER), whether or not `other` is given. After strip, `other` that contains `^`, a control character (`[[:cntrl:]]`), or is exactly `@` is `{ success: false, error: :invalid }` and sends no RPC. Ordinary text still files. A nil reply, `[Errors]` or `[BEGIN_diERRORS]`, or a reply with no `[Data]` (V0) or `[BEGIN_diDATA]`..`[END_diDATA]` (V1) data section on the date list, or a nil reply, an error, or a reply with no `[Data]` (V0) or `[BEGIN_diDATA]`..`[END_diDATA]` (V1) data section on a SOGI value-list read, is `{ success: false, error: :lookup_failed }` and files nothing. The broker's empty answer is `[Data]` or `[BEGIN_diDATA]`..`[END_diDATA]` with no rows, which stays an empty list (`entries` `[]`, `error` false).

Gender identity and sexual orientation are one DDR FILER call in mode `ADD` (`UPDATE^DIE`) whether or not the date row exists. `S9394^AUPNSOG3` makes two `UPDATE^DIE` calls (the header, then the values and the deletes). This gem makes one, so a refused add cannot follow a delete. Mode `EDIT` is `FILE^DIE`. `FILE^DIE` rejects `"+n"` placeholders (`The IENS '+2,3260115,990042,' is syntactically incorrect.`) after the same call has already deleted sub-entries whose `.01` is `"@"`, so an existing-date SOGI write does not use `EDIT` and does not delete values in one call and add them in another. No date row, including an empty `[Data]` or `[BEGIN_diDATA]`..`[END_diDATA]` section (`entries` `[]`, `error` false, which is what an empty subfile answers), is header IENS `"+1,<dfn>,"` with placeholder 1 DINUM'd to the date (`DDR3.m:12-13`) and each value `"+n,+1,<dfn>,"` DINUM'd to its code IEN. A row whose first piece equals the requested FileMan date is header IENS `"<fmdate>,<dfn>,"` (the stored subscript, no placeholder). Each new value is `"+n,<fmdate>,<dfn>,"` pinned to its code IEN, placeholders starting at 2. Each dropped value is `"<code>,<fmdate>,<dfn>,"` with `.01` `"@"`. A value already stored is not re-added. The header IENS is `$S($D(^AUPNPAT(PAT,93|94,EDT)):EDT,1:"+1")` (node 93 sexual orientation, node 94 gender identity).

Legal sex and MBI use mode `EDIT` (`FILE^DIE`) when the date row exists, at IENS `"<fmdate>,<dfn>,"`. Those rows have no `"+n"` placeholders, and that `EDIT` works live. No such row is mode `ADD` at `"+1,<dfn>,"` with placeholder 1 DINUM'd to the date. `SETLSEX` chooses the IENS with `$S($D(^AUPNPAT(PAT,92,EDT)):EDT,1:"+1")` (node 92). `ADDMBI^AUPNMBI` (`AUPNMBI.m:6`) uses `"?+1"` when `^AUPNPAT(PAT,44,EFFDATE)` exists.

- **Gender identity.** `values` are internal IENs in `#9999999.104`, not labels. Each value is filed once. `S9394^AUPNSOG3` files the value multiple as `FDA(SF,"?+"_CNT_IENS,.01)` with `RES(CNT)` equal to the code IEN, and `G9394^AUPNSOG2` reads that value from the sub-entry subscript, so the subscript has to be the code IEN. On a new date, placeholder 1 is the date and placeholders 2, 3, ... are pinned to each value's IEN. On an existing date, DDR LISTER reads `#9000001.94011` (`.01I`) and the header, the new values, and the dropped values are still that one mode `ADD` call: header IENS `"<fmdate>,<dfn>,"`, each new value `"+n,<fmdate>,<dfn>,"` DINUM'd to its code IEN (placeholders starting at 2), and each dropped value `"<code>,<fmdate>,<dfn>,"` with `.01` `"@"`. A code already stored is not re-added. The `"@"` rows and the `"+n"` rows are not split across calls, and the call is not mode `EDIT`. Before that list, each distinct value is read with DDR GETS ENTRY DATA on `#9999999.104` (IENS `"<ien>,"`, fields `"1"`, flags `I`), whether or not `other` is given. `SETGI` passes values through `$$GI^AUTSOGI(val,"I")`, which returns `""` for an unknown record, so nothing is filed for it. A genuine `[ERROR]` reply is that unknown record: `{ success: false, error: :invalid }` and nothing is filed, including no date-row lookup. A reply with neither `[Data]` nor `[ERROR]` and no field rows (`malformed: true`) is `:lookup_failed` and the message names the file and field. A nil reply is `:lookup_failed`. A `[Data]` reply with no row for field `1` is `:lookup_failed` (an empty field still comes back as a row), and nothing is filed. Field `1` CODE is piece 2 of the 0 node. The same reads decide OTHER. `S9394^AUPNSOG3` always sets `FDA(SF,IENS,2)=OTH`, where `OTH` is `""` unless a chosen value's CODE is `OTH` and the text is non-blank. This method always files field `2` on that one ADD call: the text in that case, otherwise `""`, which clears text already stored on the date. `other` text when no chosen value's CODE is `OTH` is `:invalid` and files nothing. After strip, `other` that contains `^`, a control character (`[[:cntrl:]]`), or is exactly `@` is `:invalid` and sends no RPC, before the code read. Ordinary text still files. DDR GETS of field `.02` replies `error: true` (`^DD(9999999.104,.02)` does not exist). An omitted `date` is the client's today; `FILEC^DDR3` would not default it. `AGI1`/`AGI2` (`AUPNSOGX`) fire on the write. Any code translation or other default inside `SETGI^AUPNSOGI` does not run.
- **Sexual orientation.** Same shape on `#9000001.9301` / `#9000001.93011` and on `^AUPNPAT(PAT,93)`, including the one mode `ADD` call when the date row already exists, with values as internal IENs in `#9999999.103`. `S9394^AUPNSOG3` makes two `UPDATE^DIE` calls; this gem makes one so a refused add cannot follow a delete. Each distinct value is read on `#9999999.103` field `1` the same way (`$$SO^AUTSOGI(val,"I")`). Field `2` is always filed: the text when a chosen value's CODE is `OTH` and the text is non-blank (`$$SO^AUTSOGI(val,"C")`), otherwise `""`. After strip, `other` that contains `^`, a control character (`[[:cntrl:]]`), or is exactly `@` is `:invalid` and sends no RPC, the same check as gender identity. Ordinary text still files. `ASO1`/`ASO2` fire. `SETSO^AUPNSOGI`'s own translation and defaults do not run.
- **Legal sex.** `sex` must already be `M`, `F`, or `X`. `MALE` / `FEMALE` are not translated. `source` must already be the `#9000030` IEN. `DATE ENTERED` (field `3`) is the client's `Date.today`, not the server's `DT`. A second call for the same date edits that `#9000001.9201` row in place. `SETLSEX^AUPNSOG3` is not called.
- **MBI write.** The MBI is uppercased here, the way `ADDMBI^AUPNMBI` uppercases it before `UPDATE^DIE`. `DATE ENTERED` is the client's today. `ENTERED BY` is the signed-on `DUZ`; there is no RPC when the client has no `DUZ`. `ADDMBI^AUPNMBI` always sets `FDA(SF,IENS,2)=$G(SOURCE)` (`AUPNMBI.m:19`). On an existing effective-date row the EDIT call files field `2` as `"@"` when `source` is omitted, which clears a source already stored, and files the source when one is given. On a new row, `source` is filed when given and omitted when it is not. A second call for the same effective date edits that `#9000001.44` row in place. Field `1`'s triggers and xrefs fire. Any other check inside `ADDMBI^AUPNMBI` does not run. An 11-character alphanumeric check is local; FileMan can still refuse the value, and that comes back as `:filer_failed`.
- **MBI read.** This is DDR LISTER, not `GETMBI`/`HISTMBI^AUPNMBI`. Before the list, DDR GETS ENTRY DATA reads `#9000001` `.01` (IENS `"<dfn>,"`, flags `I`). `#9000001` is DINUM'd to the DFN, so a missing entry is the error reply GETS gives for an absent record. A nil reply, an error reply, or a `[Data]` reply that omits the `.01` row raises `Client::RpcError` and `#9000001.44` is not listed. Rows are the subfile as stored (`effective_date`, `mbi`, `source`). A "current MBI" choice those tags might make is not applied. A failed list (no reply, `[Errors]` or `[BEGIN_diERRORS]`, or a reply with no `[Data]` (V0) or `[BEGIN_diDATA]`..`[END_diDATA]` (V1) data section) raises `Client::RpcError`; it is not turned into `[]`. `[Data]` or `[BEGIN_diDATA]`..`[END_diDATA]` with no rows is `[]`. Field `1` MBI is required in the DD, so a listed row whose MBI is blank raises `Client::RpcError` as well.

A repeated call for the same date writes the row already stored there, so it does not add a second date row and does not come back as "already exists". Gender identity and sexual orientation do that in one mode `ADD` call. Legal sex and MBI do it in mode `EDIT`. `retry_safety.yml` classes `set_gender_identity`, `set_sexual_orientation`, `set_legal_sex`, `add_mbi`, and `set_sex` as `non_idempotent_write`. The edit fires the field xrefs again, legal sex and MBI store `DATE ENTERED` as the client's today, and the call binds `CIAV VUECENTRIC` (restore is best-effort). `idempotent_write` in that table is a write the server dedupes, and none of these is.
- **Holidays.** `.01` DATE (DINUM) and `2` NAME are the fields that are filed. NAME longer than 30 characters, blank, or (after strip) containing `^`, a control character (`[[:cntrl:]]`), or exactly `@`, is refused before any RPC (`{ success: false, error: :invalid }`). Ordinary text still files. `GO^SDHOL`'s interactive `DIC`/`DIE`, and any default it would stuff, does not run. The `B` xref is the file's only xref and FileMan maintains it. Remove looks that xref up with DDR LISTER and deletes by editing `.01` to `"@"`. A date with no row, including `[Data]` or `[BEGIN_diDATA]`..`[END_diDATA]` with no rows, is `:not_found` and does not file. A failed lookup (no reply, `[Errors]` or `[BEGIN_diERRORS]`, or a reply with no `[Data]` (V0) or `[BEGIN_diDATA]`..`[END_diDATA]` (V1) data section) raises, for `holidays` and for `remove_holiday`; it is not reported as not-found. `[Data]` or `[BEGIN_diDATA]`..`[END_diDATA]` with no rows is an empty list.

## Sex

`Registration.set_sex` is resolution 2. `SEXELIG^AGUTL` (`AGUTL.m:51`) is the BPRM `AG_SetPatientGenderQ` target. It reads `#2` `.02` internal and `UPDATE^DIE`s `#9000003.11` `.08` GENDER (each sub-entry of every `#9000003` entry on `^AUPNMCR("B",DFN)` whose `.01` is the DFN), `#9000004` `.07` SEX OF INSURED (`^AUPNMCD("B",DFN)`), and `#9000005.11` `.08` GENDER (`^AUPNRRE("B",DFN)`). It is not a cross-reference, so a `#2` `.02` write alone does not run it. No `#8994` entry reaches it. Callers are `AG2A` (roll-and-scroll) and the `AG71A11` KIDS post-install.

`AG2A.m:58-64` files `#2` `.02` interactively first and, when that sex changed, deletes `#9000001` `.23` SSN VERIFICATION STATUS, then calls `SEXELIG^AGUTL`. This method deliberately differs from that order. It files the `.23` delete first (only when the pre-read says the sex changes and `.23` is non-blank), then `#2` `.02`, then the cascade, each as DDR FILER mode `EDIT` (`FILE^DIE`) under `CIAV VUECENTRIC`. The end state on success is the same as `AG2A`'s. Filing `.02` first left a failed `.23` delete unrepairable: the retry pre-reads the new sex and skips the delete, so SSN VERIFICATION STATUS stays set for a sex that changed. With `.23` first, a half-done run leaves `.23` cleared and `.02` unchanged. A retry sees the stored sex differ from the code and `.23` blank, skips the delete, files `.02`, runs the cascade, and finishes. `#2` `.02` is the set `M`/`F`/`U`. Its traditional xrefs and trigger (ASX, AENR02, IVM02, AVAFC02, ADGRU02, the trigger to `.083` CHECK FOR DUPLICATE, AAVABDW2) are FileMan and do fire on that `EDIT`. DDR FILER mode `EDIT` on `#2` `.02` was verified live.

`sex` must already be `M`, `F`, or `U`. It is stripped and upcased. `MALE` / `FEMALE` are not translated. A DFN that is not a positive integer, or any other sex, is `{ success: false, error: :invalid }` and sends no RPC.

The DDR reads and writes run inside `Agg.editing(dfn: id)`, the same edit lock `Registration.update` takes (`AGG LOCK PATIENT` then `AGG UNLOCK PATIENT`, under `AGGRPC`). A lock that is not taken returns Agg's failure hash and sends no DDR call: `{ success: false, error: :lock_failed, message: }` when the lock is held elsewhere (the message names who) or gives no reply, and `{ success: false, error: :invalid_dfn, message: }` when the result is `-1`. Unlock is not sent when the lock was not taken. When the lock is taken, unlock always follows, including when a later read or write fails. The DDR calls inside the lock bind `CIAV VUECENTRIC`.

Before any write, DDR GETS ENTRY DATA reads `#2` `.02` and `#9000001` `.23` (IENS `"<dfn>,"`, flags `I`). A nil reply, a `[Data]` reply that omits the field row, or a reply with neither `[Data]` nor `[ERROR]` and no field rows (`malformed: true`) is `{ success: false, error: :lookup_failed }` and files nothing. The nil and malformed messages name the file and the field. A genuine `[ERROR]` reply is `{ success: false, error: :not_found }` and files nothing. DDR GETS returns a row for an empty field, so a missing row under `[Data]` is not that `[ERROR]` reply.

It then lists the `B` xref of `#9000003`, `#9000004`, and `#9000005` (`fields` `"@;.01I"`, `flags` `"IP"`, `xref` `B`, `from` one below the DFN, `max` 100). `FROM` is exclusive. A row whose `.01` is not this DFN is ignored. For each `#9000003` and `#9000005` row that matches, DDR LISTER reads subfile `.11` (`iens` `",<ien>,"`, the same fields and flags). A nil reply, `[Errors]` or `[BEGIN_diERRORS]`, or a reply with no `[Data]` (V0) or `[BEGIN_diDATA]`..`[END_diDATA]` (V1) data section on any of these lists is `:lookup_failed` and files nothing. `[Data]` or `[BEGIN_diDATA]`..`[END_diDATA]` with no rows is an empty list. A `MORE` line on a subfile list is `:lookup_failed`: the flat DDR parameter cannot carry `FROM("IEN")`, and those subscripts are not unique, so the list cannot be resumed. A `MORE` line on the `B` list is `:lookup_failed` unless the last returned row's `.01` is a DFN past this patient. That later row means this page already holds every `B` entry for this DFN. A page that ends on this DFN, or that has not reached it, is incomplete.

The writes are separate mode `EDIT` calls, in this order. This order deliberately differs from `AG2A`, which files `.02` interactively first. Filing `.02` first left a failed `#9000001` `.23` delete unrepairable: a retry pre-reads the new sex and skips the delete, leaving SSN VERIFICATION STATUS set for a sex that changed. With `.23` first, a half-done run leaves `.23` cleared and `.02` unchanged, and a retry finishes the job. The end state on success is the same as `AG2A`'s.

1. When the stored `.02` (stripped, upcased) differs from the new code and `.23` is non-blank, `#9000001` `.23` is set to `"@"`. An unchanged sex, or a blank `.23`, skips this call. `clear_ssn_verification?` is that predicate, decided from the pre-reads on every call, including a retry.
2. `#2` `.02` is filed with the internal code, whether or not it changed.
3. When any eligibility row was found, one `EDIT` files them all: `#9000003.11` `.08` on each sub-entry, `#9000004` `.07` on each matching entry, `#9000005.11` `.08` on each sub-entry, in that file order. This is the `SEXELIG^AGUTL` cascade. It always runs, including when sex is unchanged. A `:partial` on the cascade is retried by repeating the call: the cascade runs again when rows exist and the earlier EDITs on that call succeeded.

The writes are not atomic. A refusal of the first call, or a reply with no `[Data]`, is `{ success: false, error: :filer_failed }` and later calls are not sent. nil only when that first DDR FILER call gives no reply. A reply that arrives without `[Data]` is not a no-reply: `filer` sets `success` false, so the first call is `:filer_failed` and a later call is `:partial` with the refusal wording.
